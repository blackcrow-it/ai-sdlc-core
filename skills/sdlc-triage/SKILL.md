Triage the issues that arrive on this project's tracker: bug reports and feature requests **you did not write**. Task issues (titled `TASK-NNN: ...` or labelled `sdlc`) are already agent-ready by construction; never triage them.

## Setup

- `<CORE>` is the `ai-sdlc-core` skill directory next to this skill's base directory (otherwise `.claude/skills`, `.agents/skills`, `~/.claude/skills`, `~/.agents/skills`). `SDLC` = `python "<CORE>/scripts/sdlc.py"`. Run `SDLC validate`; without a config, recommend /sdlc-setup and stop.
- Use the tracker in `.ai-sdlc/project.json` with the commands of `<CORE>/references/trackers/<tracker.provider>.md`. With the `local` tracker there is no incoming queue: say so and stop.
- Reference docs: [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) for the `.out-of-scope/` knowledge base; `<CORE>/references/TASK-AUTHORING.md` for writing task contracts.
- When preparing an agent-ready contract, follow core `references/DOCUMENTATION-CONTINUITY.md`: assess affected
  canonical documents, include `documentation`, and account for missing baselines or prerequisite approvals.

Every comment or issue you post during triage starts with:

```
> *This was generated by AI during triage.*
```

Posting, labelling and closing are visible to others: before each write, show the user exactly what you will post or change and wait for their go-ahead.

## Roles

Two **category** roles: `bug` (something is broken) and `enhancement` (new feature or improvement).

Five **state** roles:

- `needs-triage`: a maintainer needs to evaluate it;
- `needs-info`: waiting for the reporter;
- `ready-for-agent`: fully specified; tracked by a task contract that an agent can take;
- `ready-for-human`: needs a human to implement or decide;
- `wontfix`: will not be actioned.

Label strings come from `tracker.triage_labels` in the project config; a role missing there uses its own name. Every triaged issue carries exactly one category and one state label. Conflicting state labels: flag them and ask the maintainer before anything else.

Transitions: unlabelled → `needs-triage` → `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`; `needs-info` returns to `needs-triage` when the reporter replies. The maintainer may override at any time; flag transitions that look unusual and ask.

## Invocation

The maintainer describes what they want in natural language, for example "what needs my attention?", "let's look at #42", "move #42 to ready-for-agent", "what is ready for agents?". Interpret it and act.

## Show what needs attention

Query the tracker and present three buckets, oldest first: **unlabelled** (never triaged), **`needs-triage`**, and **`needs-info` with reporter activity since the last triage notes**. Show counts and one line per issue; let the maintainer pick.

## Triage one issue

1. **Gather context.** Read the whole issue: body, comments, labels, author, dates. Parse earlier triage notes so you never re-ask resolved questions. Explore the codebase with the `GLOSSARY.md` vocabulary and the ADRs in the area. Then two checks: (a) **redundancy**: search for an existing implementation of the requested behaviour by domain concept, not just the issue's wording, and report where you looked; (b) **prior rejection**: read `.out-of-scope/*.md` and surface any concept that matches.
2. **Recommend** a category and state with your reasoning, plus a short summary of the relevant code (including whether it already exists). Wait for direction.
3. **Verify the claim** before any grilling. For a bug, reproduce it from the reporter's steps (call the Skill tool with "sdlc-debugging" and work its Phases 1 and 2 only: a red-capable loop and a minimised repro, no fix). Report: confirmed (with the code path), not reproduced, or insufficient detail (a strong `needs-info` signal). A confirmed repro makes a far stronger task contract.
4. **Grill if needed.** If the request needs shaping, call the Skill tool twice, for "sdlc-grilling" and "sdlc-domain-modeling", and use the permitted interactive question tool in small independent batches, updating `GLOSSARY.md` and ADRs as actual answers settle decisions.
5. **Apply the outcome:**
   - `ready-for-agent`: write one or more task contracts per TASK-AUTHORING, with the issue's URL or key in `input_artifacts`, a confirmed repro as the first acceptance criterion's scenario, and `test_seams` for implementation roles. Validate and publish them like any task. Then comment on the source issue `Tracked as TASK-NNN: <title> (<link>)` and label it. The source stays open until its tasks are accepted; the tracker's "Close" recipe closes it then.
   - `ready-for-human`: post a **human brief** comment with the same structure as a task (summary, current and desired behaviour, acceptance criteria, out of scope) plus why it cannot be delegated (judgement call, external access, design decision, manual testing).
   - `needs-info`: post the triage notes below.
   - `wontfix`, by reason: **already implemented** → point to where it lives (never write `.out-of-scope/` for this); **rejected bug** → a polite explanation; **rejected enhancement** → write or extend the `.out-of-scope/` file, commit it, link it from the comment. Then close.
   - `needs-triage`: apply the label; comment only if there is partial progress worth keeping.

## Quick state override

"Move #42 to ready-for-agent" means the maintainer has decided: skip grilling, show what you will do, then act. Moving to `ready-for-agent` always needs a valid task contract; draft it with them if none exists.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage notes

**What we have established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything settled under "established so far" so it is not lost. Questions must be specific and answerable, never "please provide more info". Mention the reporter's real handle only.

## Resuming

When earlier triage notes exist, read them, check which questions the reporter answered, and present the updated picture before continuing.
